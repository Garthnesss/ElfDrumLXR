## Morph fix (Oct 29, 2026 — Garth's Live report: "morph slider doesn't seem to work")
- **Root cause, proven headlessly before touching code:** Phase 1 made the *previously loaded* kit the morph target, so at startup the target **was** the current kit (INIT morphing into INIT) — and until a second, different kit was loaded, the slider crossfaded a kit into itself: inaudible by construction. The target was also invisible and not settable in the UI. The machinery itself was never broken, and nothing needed ticking: the plugin doesn't compile the firmware's `presetManager` (FatFs), so `preset_morph_tick` never runs — `lxr_morph_kit` + the CC edit-diff path is the one-shot equivalent, verified end-to-end.
- **Before numbers** (`plugin/render/PluginMorphTest.cpp`, new harness): startup sweep morph 0→1 — drum peaks 14631/14585/18642/20244 → 14638/14566/19949/20179, *no systematic change* (dead slider reproduced). With target = fx-dist loaded, morph 1.0 reached only 17348/15177/20204 vs a full fx-dist load's 25506/25506/25493 — see the routing caveat below before calling that a bug.
- **Firmware morph caveat (faithful behaviour, not a plugin bug):** morphing **never** touches audio routing (params 215–220), velocity destinations (149–154) or LFO targets (167–172) — the same keep-set in `preset_morph_tick` and `lxr_morph_kit`. fx-dist differs from INIT almost only in routing + FX params, so its FX routing is unreachable by morphing, on the real hardware too. A fair morph proof needs a target differing in *morphable* parameters: `tests/kits/morph-target.SND` (INIT + drum coarse pitches 95/105/100 + snare filter freq 30).
- **Proof with the fair target:** drum peak frequencies, morph 0 = **48/95/232 Hz** (== INIT full load), 0.5 = **312/595/772 Hz** (in between), 1.0 = **1975/3773/2637 Hz == the morph-target full-load reference to the FFT bin**, on the pre-fix code already — the interpolation path (APVTS poll → `lxr_morph_kit` → edit-diff CC replay) was sound whenever a distinct target existed.
- **Fix** (remote `7ce4610`): explicit morph-target loading. Processor gains `loadMorphTargetFile()` / `getMorphTargetName()`; the editor gains a **"Morph target:" row naming the target + a "Load target .SND" button**, and dropping a .SND onto the morph rows sets the target. Loading a kit still makes the previous kit the target (its name now shown). State format v2 appends the target name; v1 state still loads. After-fix `target` flow (fresh start → load target → sweep): **48/95/232 → 312/595/783 → 1975/3772/2625 Hz**, editor-facing names read `Initkit / MorphTgt`.
- **Save loose end CLOSED:** the harness `save` mode loads a kit, saves via the processor's `saveKitFile`, byte-compares and reloads: **PASS for fx-dist and morph-target** — 255 B, parameter bytes 8..255 identical, name bytes preserved, reload renders the source kit (fx-dist peaks 25506/25506/25493). No code fix was needed; it had simply never been exercised.
- **Gates after the fix:** plugin INIT @ 44,140 Hz still **bit-exact** vs the Phase 0 golden (drums 1–2 max|diff| 0 over 20,000 onset-aligned frames; drum3's peak level varies run-to-run — pre-existing voice variance, present in pre-fix renders too); `make test` green (intrinsics 28/28 + MIDI parser). Mac: universal rebuild + harness target/save modes pass on the Mac; VST3 + AU re-signed and **reinstalled**; Mac `plugin_render` peaks 13920/14585 match Linux.
- **Harness gotcha:** a headless host must pump the message loop after `loadKitFile` or `bridgeSuspended` never clears and *all* bridge edits (not just morph) silently do nothing. Real DAWs pump continuously; only the harness needed an explicit settle step — worth remembering before diagnosing another "dead parameter" headlessly.

## Phase 3 discovery (Oct 29, 2026 — from vendor source, before building)
One focused pass over `vendor/lxr-02/Core` (`Sequencer/sequencer.c` all 2,804 lines, `sequencer.h`, `SeqStep.h`, `clockSync.c`, `Soundengine.c`, and the pattern/song sections of `Preset/presetManager.c`). The ROADMAP's four questions, answered:

- **(a) Editing semantics — there are no substeps in this firmware revision.** The sequencer's own comments say it outright ("we only have mainsteps now", "sub steps are ditched"). The grid is **64 slots per track per pattern = 16 steps × 4 bars**. The array *named* `seq_subStepPattern[64][7][64]` holds one 7-byte `Step` record per main-step slot (historical name only; `sizeof(Step)` = 7, verified by compile): `{volume (bit 7 = vestigial active flag, bits 0–6 = velocity), prob (0–100), note, param1Nr, param1Val, param2Nr, param2Val}`. A step **sounds** iff its bit is set in `seq_mainSteps[bar][pattern][track]` (uint16 masks; `seq_intIsMainStepActive`) — the volume active-bit test (`seq_intIsStepActive`) is dead code that returns 1 unconditionally, and `seq_toggleStep` flips a bit playback ignores. Per-step timing is a separate 1-byte `StepTiming {flam:4, shift:4}` array (`seq_stepTiming`): flam 0–5 maps through `flamIdxToPattern` to ×1/×2/×3/×4/×6/×8 retrigger patterns across the step's 24 prescale ticks; shift raw 0–14 = −7..+7, ×3 micro-ticks each (raw 7 = centre). Per-track `length[pattern][track]` (default 16, **0 also means 16**) wraps `seq_stepIndex[track]` independently per track (polymeter is native); wrap also at 64. The firmware's own edit functions are the API the plugin reuses: `seq_toggleMainStep`, `seq_setMainStep`, `seq_isMainStepActive`, `seq_clearTrack`, `seq_clearPattern`, `seq_copyTrack`, `seq_copyPattern`, `seq_clearAutomation`. Clear defaults (`seq_resetNote`/`seq_clearTrack`): note 60, prob 100, volume 127, p-locks = `NO_AUTOMATION` (0xFF), flam 0 / shift 7, main steps off (except the vestigial volume bit set every 8th slot), length 16. **P-lock destinations are parameter indices in the firmware's CC space** (`autoNode_updateValue` literally sends CC `param1Nr`, or CC2 `param1Nr−128`, into `midiParser_ccHandler`) — i.e. kit-parameter indices 0–246 carry the Phase 2 metadata names; this is *not* the 229-entry LFO mod-target list.
- **(b) .PAT layout (per pattern, from `preset_savePatternSD`/`preset_readPatternData`, `STEPS_PER_PATTERN` = 64):** 8-byte pattern name + `"PatV03"` (6 B) + for trk 0..6: `Step[64]` (448 B) then `stepTiming` uint8[64] (64 B) + for trk 0..6: 4 × uint16 LE `seq_mainSteps[bar][pattern][trk]` (56 B) + `shuffle[pattern]` (1 B) + `length[pattern][0..6]` (7 B) + `kitNr[pattern]` (1 B) = **3,663 bytes**. Reader versioning: no `PatV` tag ⇒ V1 (the reader rewinds 6 bytes; V1 has no timing — timing is read only when version > 2 — and no kitNr, read only when version > 1). The `tmp.pat` variant prepends a 1-byte pattern number to the same block (no name/version). Projects (PROJnn folders) hold one such file per slot plus kit and song files, loaded per slot by `loadTmpFolderFiles`. **Normalisation (plugin-defined, firmware leaves it open):** every byte of the 3,663 is structurally defined, so round-trip is byte-exact; the only plugin-side choice is the 8 name bytes, which the plugin stores per pattern in its own state (firmware keeps them in `savefileNames`, which lives in the uncompiled presetManager) — export writes the stored bytes verbatim, import stores them verbatim, default is 8 spaces.
- **(c) Song storage + chaining — chaining as the brief imagined it does not exist.** The old `PatternSetting {changeBar, nextPattern}` struct (incl. the SEQ_NEXT_RANDOM 64 / RANDOM_PREV 65 modes) is **commented-out dead code**, and its call site in `seq_nextStep` is `#if 0`'d. Live rules in `seq_determineNextPattern`: song mode ON → advance `seq_songPositionPointer` (wraps at 64) and play `seq_activeSong[pos]`; song mode OFF → the active pattern repeats forever (no per-pattern next). Song data lives **in pattern-set RAM**: `seq_songData[64][64]` — one 64-entry song per kit slot; the active kit slot's song is `seq_activeSong`. Entries: 0–63 = pattern, **64 = SONG_END (sequencer stops), 65 = SONG_LOOP (jump to song start)**. On disk a song is its own file: 8-byte name + the 64 data bytes (`preset_saveSongSD`/`preset_loadSongSD`). Pattern switching: `seq_setNextPattern` sets `seq_pendingPattern`; immediate when stopped, otherwise applied in `seq_nextStep` when the **longest track** wraps (`seq_setPendingPatternActive` — applies the pattern's shuffle, optionally autoloads its kit when `PAR_PATTERN_MODE == 1`, sends program change + note-off-all). **Backup-buffer caveat:** switching first copies `patternBackupBuffer` *over the pattern being left* (live RAM edits are discarded) and snapshots the incoming pattern into the buffer; `preset_savePatternRAM` to the current slot = copy-to-backup (makes edits permanent). The plugin wrapper therefore refreshes the backup buffer from the live pattern before switching away, treating plugin RAM edits as authoritative — documented in ARCHITECTURE. (In the plugin build the kit-autoload target `preset_loadDrumsetRam` is a host stub, so pattern changes never switch kits here — the DAW owns kit state.)
- **(d) Cadence — what `soundengine_process()` does that the plugin must replicate.** On hardware (TIM2 ISR, 64-sample blocks) it is: `seq_tick()` → `soundengine_calcNextSampleBlock()` → `uart_processMidi()` → `usb_tick()` → `preset_morph_tick()`. `systick_ticks` is a free-running ~0.25 ms counter (TIM14 ISR; **4,000 units/s**, a plain `volatile uint32_t` in our `engine/stubs.c` that nothing advanced until now). `seq_tick()` internal-clock path: when `systick_ticks − seq_lastTick ≥ seq_deltaT`, advance **one** prescale tick and fold the overshoot into the next interval. `seq_deltaT = (60000/BPM)/96×4` systick units = one 96-ppq pulse; `seq_prescaleCounter` cycles 0..23 (**24 ticks per 16th step**); at counter 0 → `seq_nextStep()`; `seq_processFlam(counter)` runs every tick; MIDI clock out every 4th tick (24 ppq). Shuffle stretches/shortens alternate steps via `seq_masterStepCnt` parity in `seq_calcDeltaT`. `seq_setBpm` takes a **uint16 — firmware BPM is integer**. Of the surrounding calls: `preset_morph_tick` is presetManager code (not compiled; the plugin's morph is the wrapper's one-shot equivalent — nothing to replicate), `uart_processMidi` ≙ the plugin already feeds bytes via `lxr_midi_bytes`, `usb_tick` is a no-op stub. **External MIDI clock is fully implemented upstream**: `midiParser_parseUartData` routes CLOCK/START/CONTINUE/STOP to `seq_sync()`/`sync_midiStartStop` when `seq_getExtSync()` is set (`clockSync.c` advances a step per 6 clocks, window-averages BPM, applies shuffle delay); ext sync is armed from the front panel (`seq_setExtSync(1)` = MIDI), so the wrapper exposes that setter and the processor forwards realtime bytes it previously dropped. Probability rolls use `GetRngValue()` = the HAL hardware-RNG stub — gate scripts therefore use prob=100 for exact trigger-log equivalence and exercise probability statistically. One quirk to respect: `seq_setTrackLength`/`seq_getTrackLength` operate on `frontParser_shownPattern`, **not** the active pattern — the wrapper writes `seq_patternSet.length[pattern][track]` directly for non-shown patterns.

## Firmware MIDI findings (Oct 28, 2026 — corrects an assumption in the original brief)
- The firmware's per-voice note parameters (`PAR_MIDI_NOTE1..7`) are **inert placeholders upstream**: the parameterArray hooks are commented out in the firmware source and `midi_NoteOverride` is disabled. The real mapping is **channel-based** via `midiParser_parseUartData` (a clean raw-byte entry exists and is what the plugin feeds). Factory defaults (`preset_loadDefaultGlobals`): all voice channels = 1, all voice notes = 48, global channel = 0 (all).
- Plugin behaviour, given that: if the seven configured notes are not all equal, notes match per-voice on configured note+channel and play at the played pitch; while stock (all 48) a GM map {36,45,50,38,39,42,46} selects the voice and pitch = 60 + (played − map note) — the same pragmatic fallback PHX-D01 used. All non-note, non-sysex/realtime MIDI is passed raw to the firmware parser (CC/NRPN edit parameters exactly as hardware front-panel/MIDI would).
- Firmware quirk reproduced faithfully (not a plugin bug): there is **no data-entry-fine (CC38) handling** after NRPN selection — a standard NRPN tail CC38=0 writes 0 into the selected parameter. Verified by test: NRPN CC2 #0 (filter drive 1) = 127 moved drum1 peak 13,921→23,260; a CC38 tail then zeroed filter freq 1 and silenced the kick, exactly as the firmware would on hardware.

The firmware's morph routing/vel-dest/LFO-target exclusions are faithful hardware behaviour and stay.
- Engine is a process-wide singleton (`std::call_once` init) — multiple plugin instances in one DAW process share the engine. **Phase 2 investigation (Oct 29):** full mutable-state enumeration completed (157 symbols / 317,047 B, no heap) — a mutex-serialised memcpy swap is feasible in size but needs per-binary post-link address tables; deferred rather than shipped half-proven (see Phase 2 section + ARCHITECTURE).
- Phase 2 metadata semantics (Oct 29): APVTS names/ranges come from the generated firmware metadata; filter-type values follow the DSP enum (1..8, 0 = bypass), not the LCD's shifted lookup; LCD long-name typos are fixed presentation-side in the generator only.
- Voice presets (Oct 29): `.lxv` slice files (magic + voice + bytes + source kit name), same-voice transfer only — slices are voice-specific index sets of different sizes (36/37), so cross-voice pasting is undefined by construction.
- Randomise guards (Oct 29): routing + mod-target selectors + morph-destination are a keep-set (morph's spirit); level params floored at 30% of range (LXR02XXL guard).
